# Playbook: 2026 — S2 Architecture

## 1. الصورة الكبيرة (60 ثانية)
تطبيق ويب أحادي الجهاز بلا خادم لمشغل الورشة: كل البيانات تعيش في تخزين محلي كسجل قيود append-only — حركة نقد مستوردة من يومية الإكسل (K-3)، التزامات، مشتريات على الدَّين، سدادات. عند كل قيد جديد يعيد NetEngine حساب الصافي = نقد − Σ التزامات، وتعرضه DashboardPanel لحظياً مع رابط لقيد مصدر كل رقم (HR-1). حسم الشهر يبني لقطة مغلقة تفصل تكلفة المواد قبل النسب المتفق عليها (HR-5, HR-6). لا خادم، لا تعدد مستخدمين، لا محاسبة مضاعفة، لا مخزون.

## 2. القرارات المعمارية (ADRs مصغّرة)

### ADR-1: تطبيق ويب محلي بلا خادم
- **القرار:** SPA يعمل على جهاز واحد؛ التخزين localStorage عبر طبقة Store واحدة؛ الواجهة React + TypeScript [افتراض].
- **السبب:** U-1/SC-1 (الصافي خلال ثوانٍ — عتبة أقل من دقيقة) + سياج MVP الذي يمنع تعدد المستخدمين وتكامل البنوك؛ لا يوجد أي طلب خادم أو استضافة في S0/S1.
- **البدائل المرفوضة:** backend + قاعدة بيانات — تعقيد وتكلفة تشغيل بلا ميزة في MVP؛ تطبيق سطح مكتب — يعقّد التوزيع بلا حاجة موثقة.
- **الأثر:** S3 يقسم الواجهة بلا طبقة شبكة؛ S4 يكتب Store أولاً قبل أي UI.
- **يحتاج قرار بشري؟** نعم — اختيار التقنية تفضيلي لأن S0/S1 لم يحددا stack. ⚠

### ADR-2: append-only ledger كمصدر حقيقة وحيد
- **القرار:** كل كيان قيد يُلحق ولا يُعدّل؛ الأرقام المحسوبة تُشتق لحظياً ولا تُخزن مطلقاً.
- **السبب:** BR-1 (كل رقم له قيد مصدر قابل للعرض) وK-1 (الثقة قبل الميزات) وK-5 (لا يوجد اليوم رقم صافٍ موثوق).
- **البدائل المرفوضة:** تخزين الصافي محسوباً — يخلق مصدرين للحقيقة وينتهك BR-1 عند أي تعارض.
- **الأثر:** S4 يمنع أي كتابة تخزين خارج Store؛ الاشتقاق الحي كافٍ لأحجام بيانات ورشة واحدة.
- **يحتاج قرار بشري؟** لا.

### ADR-3: الإكسل يبقى — استيراد لا استبدال
- **القرار:** حركة النقد تُستورد من يومية الإكسل عبر ExcelImporter؛ إدخال الالتزامات/المشتريات/السدادات يتم داخل المنتج (UF-1/UF-2 المعتمدتان).
- **السبب:** K-3 حرفياً: «أي حل يُبنى حول هذه البيانات ولا يستبدلها» — التسجيل اليومي بيد السكرتيرة قائم.
- **البدائل المرفوضة:** استبدال الإكسل كلياً — يخالف K-3 مباشرة؛ ترك كل الإدخال خارج المنتج — يفرغ UF-1/UF-2 من معناها ويعيد المشكلة الأصلية.
- **الأثر:** S3 يصمم شاشة استيراد بسيطة + نماذج إدخال؛ حدود التوزيع (ماذا يُدخل أين) تُثبت عند الـ Gate.
- **يحتاج قرار بشري؟** نعم — توزيع المسؤولية بين الإكسل والمنتج. ⚠

### ADR-4: مستحقات العاملات كالتزامات worker_accrual
- **القرار:** عند حسم الشهر تنشأ Commitments من نوع worker_accrual بمقدار payout لكل عاملة، وتُسدد عبر نفس مسار السداد C-3.
- **السبب:** SC-1 (معادلة الصافي تشمل مستحقات العاملات) + HR-5/K-4 (النسب معروضة لا معدلة) — واجهة واحدة للديون بدل حقل منفصل يخالف ADR-2.
- **البدائل المرفوضة:** حقل مستحقات خاص داخل NetEngine — مصدر حقيقة ثانٍ.
- **الأثر:** S3 يعامل مستحقات العاملات كبقية الالتزامات في CommitmentsLedger — لا شاشة خاصة.
- **يحتاج قرار بشري؟** نعم — توقيت نشوء المستحقات (عند الحسم فقط). ⚠

### ADR-5: لا نمذجة مخزون
- **القرار:** بنود المشتريات نص حر داخل CreditPurchase.items؛ لا كيان مخزون.
- **السبب:** U-4 صراحة: حالة سجل المخزون مجهولة — لا تفترض وجوده أو غيابه.
- **البدائل المرفوضة:** كيان Inventory كامل — بناء على افتراض ممنوع من S0.
- **الأثر:** S4 يستخدم string[] فقط؛ إن ظهرت حاجة مخزون حقيقية تُرفع للإنسان أولاً.
- **يحتاج قرار بشري؟** لا.

### ADR-6: لقطة الحسم مغلقة
- **القرار:** MonthSettlement تُكتب مرة عند الإغلاق ولا يُعاد حسابها؛ أسئلة الشهر المغلق تُجاب من اللقطة.
- **السبب:** HR-6/BR-6 (الشهر المغلق لا يُعاد حسابه).
- **البدائل المرفوضة:** إعادة حساب ديناميكية للشهور الماضية — تخالف BR-6 مباشرة وتفتح باب خلافات نهاية الشهر التي يريد F-5 إغلاقها (P-3).
- **الأثر:** S4 يمنع أي كتابة على settlements بعد الإنشاء.
- **يحتاج قرار بشري؟** لا.

## 3. خريطة التدفق (Flow Map)
**UF-1 — تسجيل دين مواد ورؤية الصافي (F-1, F-2, F-3):**
1. المشغل يفتح اللوحة ← DashboardPanel يستدعي C-4 getNetPosition() ← يعرض الصافي مع مصادره (HR-1).
2. يدخل مشتريات بالدَّين ← PurchaseForm يفحص HR-2/HR-7 ← C-1 addCreditPurchase() ← Store يلحق CreditPurchase + Commitment.
3. Store يبلّغ NetEngine ← إعادة حساب فورية ← DashboardPanel يعرض الصافي الجديد وأثر الشراء (U-1).
4. أي رقم جديد قابل للفتح في SourceViewer عبر C-7 (BR-1).
5. دين بلا استحقاق ← يُقبل بوسم «بلا استحقاق» ويظهر في تصنيف منفصل (HR-2).

**UF-2 — تسجيل سداد (F-4):**
1. يفتح سجل الالتزامات ← CommitmentsLedger ← يختار التزاماً ويرى المتبقي.
2. يسجل سداداً ← C-3 recordPayment() ← رفض إن لم يوجد التزام (HR-3) أو تجاوز المتبقي مع اقتراح بديل (HR-4).
3. يُلحق Payment ← NetEngine يعيد الحساب ← الصافي يتحدّث.

**UF-3 — حسم الشهر (F-5):**
1. يفتح SettlementBoard ← يطلب حسم الشهر ← C-5 settleMonth().
2. الحساب من قيود الفترة فقط (HR-6): الإيراد من CashEntry المستوردة/اليدوية (K-3)، تكلفة المواد من مشتريات الشهر.
3. تُعرض نسب العاملات كما هي بلا تعديل (HR-5) ← لقطة MonthSettlement تُغلق.
4. تنشأ التزامات worker_accrual (ADR-4) ← تُسدد لاحقاً عبر UF-2 نفسها.

**UF-4 — خارج MVP (F-6):** ممنوع بناؤه أو تجهيز بنية له (سياج MVP).

## 4. حدود التنفيذ
- **الأداء:** الصافي يظهر خلال ثوانٍ من فتح اللوحة (U-1) — بلا طلبات شبكة إطلاقاً.
- **dependencies:** لا مكتبات خارجية في MVP عدا إطار الواجهة نفسه [افتراض] — لا مكتبة محاسبة، لا ORM، لا مكتبة تقارير (NG-1 + سياج لا PDF).
- **ممنوع بناؤه:** تعدد مستخدمين/صلاحيات، تكامل بنوك/دفع، F-6، تقارير PDF (سياج MVP).
- **ممنوع لمسه:** ديون الـ 50,000$ قائمة كقيود بلا أي إعادة جدولة أو تفاوض (NG-2, K-2)؛ نموذج النسب لا يُغيّر (NG-3, K-4).
- **نزاهة البيانات:** كل كتابة تمر عبر Store حصراً — ممنوع لمس localStorage مباشرة من مكونات UI (ADR-2).
- **حد حجم المكوّن:** غير موثق في المدخل — [افتراض] مكوّن UI واحد ≤ ~200 سطر في S4؛ يُعتمد عند الـ Gate.

## 5. كيف تتحقق أن S3 التزم بهذه المعمارية
1. افتح أي رقم معروض في اللوحة أو السجل — يجب أن ينفتح قيد مصدره بلمسة واحدة (HR-1)؛ رقم بلا رابط = مخالفة قائمة.
2. أدخل سداداً لالتزام غير موجود — يجب رفض فوري (HR-3)؛ ثم سداداً أكبر من المتبقي — رفض مع اقتراح المبلغ البديل (HR-4).
3. أدخل مشتريات بلا تاجر — رفض؛ وبلا موعد استحقاق — قبول مع وسم وتصنيف منفصل (HR-2).
4. أعد طلب حسم شهر مغلق — يجب رفض إعادة الحساب والإجابة من اللقطة (HR-6).
5. قارن النسب المعروضة في الحسم مع قيم Worker.ratioPercent — يجب تطابق حرفي بلا تعديل أو تقريب من النظام (HR-5).
6. افصل الإنترنت وافتح اللوحة — الصافي يجب أن يظهر كاملاً خلال ثوانٍ (U-1/ADR-1)؛ أي نداء شبكة = مخالفة.
7. ابحث في كود S4 عن أي كتابة تخزين خارج Store — وجود واحدة يعني كسر ADR-2.
